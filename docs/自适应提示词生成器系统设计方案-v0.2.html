System Design · Revision v0.2

自适应提示词生成器：系统设计方案 v0.2

v0.1 讨论稿经外部审查后全面修订：12 项审查意见全部处置（10 项接受、2 项带理由收窄），核心变更为——评估对象拆为三对象、Patch 契约重写、范围从「大多数 Agent」收窄为「文本/系统提示词 MVP」、基准与版本记录前移、自学习数据按弱监督治理。

v0.2 修订版 响应 12 项审查意见 新增 3 份前置规范骨架 2026-10-24

v0.2 修订总览：这次改了什么、为什么

v0.1 的四项核心选择（IR+原子补丁、生成-评估-选择主干、IR 与渲染分离、L0–L3 渐进自学习）经审查确认方向成立，予以保留。本次修订不改方向，改的是工程契约与承诺边界：把「看起来自洽」的方案改成「可以被验收」的方案。

五处结构性改动贯穿全文，先在这里说清，后文按节展开：

  1. 评估对象一分为三（§3）：PromptIR（结构合法性）、RenderedPrompt（表达质量）、EvalRun（目标模型执行效果）是三种不可互换的证据。v0.1 说「所有评估发生在 IR 层面」，这句话被审查正确地判定为根本歧义，予以撤回。
  2. 单一事实源 + 统一寻址（§3.1、§4）：slots 是唯一事实源，指令清单降级为编译期派生物；Patch 全部操作改用 loc 统一寻址，并补齐 base_version、前置校验、幂等键、事务边界；COMPILE 从 Patch 类型中独立出去。
  3. 范围收窄（§2）：MVP 定位为「单轮或边界清晰的文本/系统提示词生成」，不再宣称「适配大多数 AI Agent」；消息角色、工具 schema、多 Agent 编排在能力矩阵中显式列为非目标。
  4. 基准与版本记录前移（§10）：版本化基准、人工金标与最小不可变版本记录从 P0 开始，P0 拆为 P0a（从零）/ P0b（迭代）两条独立可验收流程，消除 v0.1「迭代模式需要版本树但 P0 不做版本树」的依赖矛盾。
  5. 自学习按弱监督治理（§8）：裁决日志降格为「裁判生成的弱标签」，补 DPO 对构造规则、血缘级数据切分（防近邻泄漏）、数据卡与撤销传播；P5 改为 ROI 与瓶颈驱动，不再由数据量单一条件触发。

审查的总体结论被采纳为本次修订的基调：批准收窄后的 P0 技术验证，不按 v0.1 文本直接承诺 P1–P5 排期；不对外承诺「适配大多数 AI Agent」与「任意目标模型」。进入 P0 前先交付三份规范（§10.1），其余能力由数据与阶段门槛驱动，不由预定排期驱动。

一 / Principles v2

设计立场：三条旧铁律 + 两条新铁律

v0.1 的三条铁律（模型特异最优、评估信号上限即优化上限、相对优于绝对/结构优于措辞）经审查未受质疑，保留。本次新增两条，直接来自审查意见 1、6：

新铁律四：三种证据不可互换。结构合法（IR 静态检查）、表达质量（裁判 rubric）、执行效果（目标模型实测）分别支持不同强度的结论。任何对外结论必须注明证据层级——「渲染通过 L1」不能说成「适配该模型」，「裁判更喜欢」不能说成「效果更好」。
新铁律五：基准与版本记录先于一切自动化。没有版本化基准与不可变版本台账，就不存在可信的「回归保护」，也就不存在安全的迭代、在线改进与自学习。它们是地基，不是 P4 的装饰。

二 / Scope

范围收窄：从「大多数 Agent」到「可验收的 MVP」

2.1 场景能力矩阵

这张表同时回答审查意见 5：v0.1 的 IR 覆盖不了广义 Agent 场景是事实。修订后的定位是「面向文本与系统提示词的生成-迭代-评测系统」，Agent 编排能力通过 schema_version 预留扩展位，按场景需求逐个立项，而不是现在硬做一半。

2.2 显式非目标清单（防止范围回涨）

  • 不承诺「任意目标模型」——只承诺「模型卡登记在册的受支持模型清单」，新增模型需登记 + 基准子集实测后才宣称支持。
  • 不承诺自动删除任何安全、合规、硬格式约束（见 §6 保护类）。
  • 不承诺在无版本基准的场景下给出「效果提升」结论。
  • 不承诺 P5 权重蒸馏的必然发生——它由 ROI 触发，不由数据量触发（§8.3）。

三 / Core Objects

核心对象重构：一变三

3.1 PromptIR v2：单一事实源

v0.1 让 slots 与 instructions 并存，审查指出这是双事实源。v0.2 的裁决：slots 是唯一事实源，所有语义内容进槽位；只有确实无法结构化的表达进 freeform_extras；「指令清单」不再存储，改为编译期派生物（每个派生单元的 ID 由其 loc 确定性生成，天然可重放）。

IRv2 = {
  schema_version: "2",                      // 契约版本，未来扩展（message_plan 等）经版本升级进入
  ir_id, version, parent_ir_version, lineage_id,   // lineage：同一谱系，供数据切分用（§8.2）
  checksum,                                 // Patch 前置校验用（CAS）
  created: { by: "zero|iterate|online", strategy_id, at, operator },
  slots: {                                  // ★ 唯一事实源
    role,                                   // 角色
    goal:      { outcome, done_criteria[], non_goals[] },
    inputs:    [ { ref, type, note, trust: "user|derived" } ],
    output:    { format, schema?, length_budget },
    constraints: { must[], must_not[], style[] },
    examples:  [ { input, expected } ],
    workflow:  [ "…" ],
    feedback_protocol: { on_fail_report: "现象|复现|已尝试|影响面" }   // 新槽位：响应"反馈诊断"维度
  },
  freeform_extras: [ { id, text, provenance, protect_class? } ],       // 少数无法结构化的表达
  provenance_map: { "": { source: "user_turn:3 | seed | derived:rule7 | gen:strategy2" } },
  protect_registry: [ { loc, class: "safety|hard_format|user_pinned", by, at, reason } ],
  // 注意：不再有 instructions[] / rendered 字段——
  // 指令清单 = 编译期派生；渲染结果 = RenderedPrompt[]（独立对象）
}

三个关键设计：

  • 统一寻址 loc：形如 slots.constraints.must[0] 或 freeform_extras[F-3]。v0.1 的 ADD 用 slot、DELETE 用 ins_id 的不对称寻址被废除——所有编辑操作使用同一种 loc，role / goal / output / examples / workflow 全部可编辑，消除覆盖盲区。
  • protect_registry 保护类：任何 loc 可被登记为 safety / hard_format / user_pinned 三类保护，进入 §6 的删除豁免。安全约束可以由生成器合理补充（响应审查意见 4：未提及 ≠ 无必要），但一旦登记为保护类就退出自动删除范围。
  • lineage_id 血缘：为 §8.2 的数据切分服务——同一谱系的所有版本永不跨越训练/测试边界。

3.2 RenderedPrompt 与 EvalRun

RenderedPrompt = {
  rendered_id, ir_id, ir_checksum,
  model: { id, version_snapshot },     // 模型版本快照：供应商升级即失效，须重测
  renderer_version, decode: { temperature, max_tokens },
  text, instruction_manifest[]        // 派生指令清单（带 loc 派生 ID），供消融与归因
}

EvalRun = {
  run_id, rendered_id,
  bench: { id, version, case_ids[] },  // 用例集版本化：结果可比较的前提
  repeats: 3, metrics: { name: { mean, ci95 } },
  hard_gates: { item: pass|fail },
  failures: [ { case_id, phenomenon, loc_hint } ]   // 失败样本带可定位现象
}

缓存键设计（响应审查意见 3 的「缓存错用」）：sha256(ir_checksum + model_snapshot + renderer_version + decode)。任何一个分量变化（包括供应商静默升级模型）都会使缓存失效，杜绝拿旧渲染结果冒充新评测。

四 / Patch Contract v2

Patch 契约 v2：可校验、可重放、可事务

Patch = {
  schema_version: "2",
  base: { ir_id, version, checksum },        // 应用前 CAS 校验：checksum 不符 → 拒绝并报告基线漂移
  idempotency_key,                            // 同键重放 → 返回首次结果，不重复应用
  created: { by, at, reason, evidence_refs[] },// evidence_refs 指向 EvalRun/run_id 或会话轮次
  ops: [
    { op: "ADD",     loc: "slots.constraints.must", content: "…", provenance: "user_turn:5" },
    { op: "DELETE",  loc: "slots.constraints.style[2]", evidence_refs: ["run:881"] },
    { op: "REWRITE", loc: "slots.goal.outcome", content: "…", reason: "动词+对象+完成态重写" },
    { op: "MOVE",    loc: "freeform_extras[F-1]", to: "head" }   // 对抗中段遗忘：移位而非删改
  ],
  transaction: "all_or_nothing"              // 任一 loc 校验失败 → 整包拒绝，零部分应用
}
// COMPILE 不再是 Patch 操作——渲染是独立命令，产出 RenderedPrompt，天然可由缓存键重建

契约要点逐条对应审查意见 3：

  • 操作完备性：四种 op × 统一 loc，覆盖包括 role、goal、output、examples、workflow 在内的全部字段；不再存在「ADD 定位不到 goal」的盲区。
  • 前置校验与基线漂移：base.checksum 是 CAS 语义。迭代模式下若父版本已被其他补丁更新，本补丁拒绝应用并提示重新基于新基线生成——这同时是 §7 在线模式并发安全的基石。
  • 幂等与重放：应用器是确定性重放器（同一 Patch 对同一 base 必得同一结果），idempotency_key 保证任务重复投递不产生双重应用。
  • 事务边界：all-or-nothing。任何 loc 解析失败整包拒绝，不产生半应用的中间态——直接消灭「补丁误应用」类别。
  • 每条 op 带证据引用：REWRITE 带理由、DELETE 必带 evidence_refs（指向具体 EvalRun 或消融记录），无证据的 DELETE 在应用层直接拒绝——把「凭感觉删」从协议上排除。
Deliverable
本节将连同 §5、§9 一起，落成 P0-前置的三份规范文档（§10.1）。规范文档须附JSON Schema + 合法/非法 Patch 用例集 + 确定性应用器，用例集中刻意包含：base 漂移、loc 越界、重复投递、保护类 DELETE、空 ops——五类非法样本都必须被应用器拒绝。

五 / Evaluation v2

评估体系 v2：三层证据、人工锚点、诚实的统计

5.1 三层证据与结论边界

层级手段能下的结论不能下的结论
L1 结构检查规则引擎：槽位完整性、矛盾检测、保护类冲突、token 预算、loc 合法性结构合法、无自相矛盾、可渲染任何关于「质量」或「适配」的结论
L2 表达评估裁判按已校准 rubric 成对裁决（交换顺序双裁）候选间的相对优劣序（含平局）绝对可用性；跨任务/跨模型推广
L3 执行验证目标模型 × 版本化用例集 × 重复 ≥3，硬门 + 指标 ± CI95「适配该模型（该版本）」；回归判定对未测模型/未来版本的承诺

5.2 Rubric 校准：打断自我强化环

审查意见 2 指出的循环是致命的：M1 误解 → rubric 错 → 裁判稳定选错候选 → 学习层把错误固化。v0.2 在环上插入一个不可绕过的人工锚点，并给 rubric 自身装上回归机制：

  1. 起草：rubric v1 仍由 M1 从意图框架自动起草（这是效率来源，保留）。
  2. 用户确认（t0 锚点）：v1 必须经用户逐项确认或修订后才生效，未确认的 rubric 不允许进入任何裁决。用户在这一步的修正直接覆盖 M1 的误解。
  3. 版本化：rubric 每次变更升版本；所有历史裁决记录其 rubric 版本，跨 rubric 版本的分数不可直接比较。
  4. 周期抽检：按会话抽样（如 5%）人工复核裁决结论，报告一致率；一致率低于阈值触发 rubric 修订流程。
  5. 冲突即升级：用户实际满意度和裁判结论系统性冲突时，结论不是「用户错了」，而是 rubric 缺项 → 走修订流程并回归验证。

L2 全配对N(N−1)/2 对 × 2（交换双裁）= N(N−1)12v0.1 的「2N」有误，予以修正
双裁不一致重裁每不一致对 +10–6重裁仍不一致 → 记平局
L3 执行（深度模式）N × 用例数(默认5) × repeats(3)60仅在用户开启时发生
合计常规模式 ≈ 17–25 次调用；深度模式 +60。N>6 时改瑞士轮（O(N log N)），预算封顶可配置

未定义情形的裁决规则（全部补齐）：

  • 平局：积分制（胜 1 / 平 0.5），按积分排名；并列即并列交付，不强行分出高下。
  • 非传递性（A>B>C>A）：允许存在，报告环的存在作为证据质量警告，不掩盖。
  • 全候选不过硬门：宁缺毋滥——不产出冠军，返回前二名及失败报告，向用户呈现三个选项（放宽验收 / 人工修订 / 放弃本次生成），禁止系统「矮子里拔将军」。
  • 小样本不稳定：L3 用例数 < 5 时不输出排名结论，只输出「证据不足，需增补用例」。
  • 重复与置信区间：L3 每用例 repeats≥3（受控温度），报告 mean ± CI95；两组 CI 重叠即记「无显著差异」，不宣称提升。

降级路径（响应审查意见 12 的运维缺口）：生成器限流 → 排队退避 + 策略数 N 降为 2；裁判不可用 → 跳过 L2、直接 L3 或转人工；非法 JSON → 一次修复重试，再失败则该候选弃赛；无候选存活 → 走「全败」流程；预算耗尽 → 返回已完成层级的最优结果并明确标注证据层级不足（如「仅 L1 通过」）——绝不冒充完整结论。

六 / Deletion Logic v2

删除判定 v2：证据阶梯取代 provenance 判定

修订核心：「用户未提及」从删除依据降级为筛查信号。provenance = gen: 只提高某条指令进入复核队列的优先级，删除的唯一依据是证据阶梯走完。审查意见 4 的两种误伤（误删必要的安全/隐含步骤；无法识别真正的凭空添加）由此同时规避——前者由保护类豁免，后者由证据门槛拦截。

「冗余」与「未提及」由此获得不同的定义与不同的处置：

  • 冗余：语义等价且消融零增益（含组合消融）→ 可进入降级候选；若两条指令互为安全冗余（如同一禁令的双表述），登记为保护类而非删除——审查意见 9 关于「重复约束的安全价值」被采纳为规则。
  • 未提及：provenance 筛查 + 证据走完 + 不属保护类 → 才能作为降级候选进入人工确认。生成器合理补充的必要内容（安全、格式完整性、由目标推导的隐含步骤）在 protect_registry 登记后自然豁免。

七 / Online Mode v2

会话内改进 v2：把异步补丁变成事务

审查意见 7 判定 v0.1 的在线模式「暂不具备上线条件」，v0.2 予以接受并补齐事务语义，同时把 P1 的上线条件改为「先通过并发与乱序测试」：

  1. 会话代次（session_epoch）：任务切换、用户手动编辑、补丁应用，三者都使 epoch +1。所有在途补丁携带生成时的 epoch。
  2. CAS 应用：应用时校验 epoch + base.ir_checksum，任一不符 → 补丁作废、入重排队列（基于新状态重新生成，不是重放旧补丁）。
  3. 取消机制：用户切换任务 → 该任务名下所有在途补丁标记 cancelled；补丁生成任务本身可取消、可去重（idempotency_key）。
  4. 应用策略 v2：默认仅人工确认应用。自动应用从配置中移除，仅作为「未来研究项」保留——且即便将来启用，门槛也是「连续两次独立 EvalRun 正向 + rubric 无冲突」，而非 v0.1 的「连续两轮同一信号」（审查正确指出后者不是高置信证据）。
  5. 效果归因 v2（废除单轮回滚）：应用后进入归因窗口（≥ k 轮）；只有「连续 m 次出现同一失败签名」才判定补丁无效，执行带滞回的回滚。单轮波动（模型随机性、上下文变化）不再触发回滚——消灭应用-回滚振荡。
  6. 成本表述修正：扫描未命中时为「低成本」而非「零成本」：规则引擎、抽取器与队列调度本身仍有计算与运维开销，计入预算模型。

P1 出口判据（可执行版）：并发会话注入测试、任务切换竞态、重复投递、乱序到达四类用例全部通过；过期补丁作废率 100%；上线后误回滚 = 0（观察窗 2 周，分母为已应用补丁数）。

八 / Learning Data v2

自学习数据治理：按弱监督处理

定性修正（响应审查意见 10）：裁决日志是裁判生成的弱标签，不是免费的真实答案。它可用，但必须经过弱监督数据的全套治理：同上下文构造、去重、质量过滤、标签抽检、防泄漏切分、授权与可撤销。

8.1 偏好对（DPO 燃料）构造规则

  • 同上下文约束：chosen / rejected 必须来自同一输入上下文（同对话前缀 + 同 IR 谱系 + 同目标模型 + 同渲染与解码配置），唯一差异是候选本身。不满足则弃用。
  • 必须携带谱系标签：每对记录 lineage_id、rubric 版本、裁判 ID 与理由，供过滤与审计。
  • 去重与质量过滤：语义哈希去重；裁判置信低、双裁不一致、硬门未过的样本全部出队。
  • 标签准确率抽检：每批次人工抽检 ≥3%，报告与人工判断的一致率；低于阈值则该批次降权或弃用。

8.2 防泄漏切分（响应「版本近邻泄漏」）

切分单位不是「样本」而是血缘（lineage）：同一 IR 谱系的全部版本、其全部裁决记录，只出现在训练集或测试集之一。切分同时按租户 × 任务类型 × 会话 × 时间做分层，防止「同一用户同一任务的近亲版本」分居两个集合。测试集外另设一份从未参与任何优化的冻结金标，作为所有晋升结论的唯一仲裁。

8.3 P5 触发条件重写（响应审查意见 P2-2）

「偏好对过万」从充分条件降级为必要条件之一。启动 P5 需同时满足三条：① P4 已稳定运行且遇到明确的成本/时延/质量瓶颈（而非排期到了）；② 有独立测试集证明小模型非劣于继续调用强模型（预注册非劣效边界 ε）；③ 完整 ROI 评估（含训练与维护成本）。三条不齐，P5 不启动——数据由阶段门槛驱动，排期只是预期。

9.2 租户与数据授权

  • 隔离边界从「策略池」扩展到全部派生物：检索索引、反思笔记、策略卡、偏好对、渲染缓存，全部按租户硬隔离，并记录血缘以支持删除传播。
  • 训练 opt-in：任何用户数据进入自训练管道前需要明确授权；未授权数据只产生会话内效果（L0），不进入跨会话沉淀（L1+）。
