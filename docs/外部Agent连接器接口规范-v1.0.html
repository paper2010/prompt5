Companion Spec · Connector Interface v1.0

外部 Agent 连接器接口规范

在系统设计方案 v0.4 的既有契约之上，预留并冻结一套标准化连接器接口：外部 Agent 以「适配器 + 配置 + 契约测试」的方式接入，核心模块（M1–M8）零改动。本规范直接复用 v0.4 的错误码体系、幂等语义、CAS 四元组、canonical JSON、预算治理与保护类三权，不新造并行机制。

v1.0 · 契约冻结版 9 项能力 · 2 种绑定 TCK 硬门接入 2026-10-24

零 · 定位与边界：这是「接口预留」，不是「范围扩张」

v0.2 曾把范围收窄为「面向文本与系统提示词的生成-迭代-评测系统」，并立了防回涨清单。连接器接口与本原则的关系必须先说清楚：本规范冻结的是「如何被外部调用」的契约，不扩大「能被调用做什么」的范围——外部 Agent 通过连接器得到的，始终是 MVP 范围内既有的能力面。

本版冻结 / 本版不做
冻结（现在定死，后续只做加法）：Port 定义、公共信封、9 项能力的请求/响应契约、错误码映射、webhook 事件格式、TCK 用例集、连接器配置 Schema。核心模块自 P0 起即按 Port 编程，适配器实现随各阶段就绪。
不做（防回涨）：不做无状态网关模式（会破坏单一写者不变式）；不向连接器开放台账写入、保护类批准、模型卡直写；不因外部接入而扩展到消息编排 / 工具 schema 等 v0.2 已裁定的非目标。

一 / Architecture

架构位置与五条耦合规则

1.1 Port / Adapter：依赖倒置的接入面

1.2 五条耦合规则（松耦合的来源）

规则内容为什么
① 依赖倒置核心只依赖 Port 接口；适配器实现 Port 反向注入。编译期架构测试强制：核心包 import 列表中禁止出现任何适配器。新协议接入不改核心，这是「零改动」承诺的机械保证，而非口头约定。
② 配置驱动注册一个新连接器 = 一条注册配置（租户、scopes、token、预算、回调），不是一段代码。接入是数据操作，可审计、可撤销、可配额。
③ 能力协商客户端先 GET /v1/capabilities 再调用；服务端逐能力声明版本与状态（stable / beta）。双方按声明的交集工作，不硬编码假设；新能力上线不破坏旧客户端。
④ 宽容读者 + 附加演化双方必须忽略未知字段；同一主版本内只允许附加性变更（新增可选字段、新增能力），禁止改语义、删字段、改必填。核心演进与外部客户端解耦——这是「后续新 Agent 无需修改核心」的对称面：核心演化也无需外部 Agent 改代码。
⑤ 私有扩展隔离一切非标扩展放 extensions{} 信封字段，键名强制 x- 前缀命名空间（如 x-acme-cache-hint）；系统对未知 x- 字段只透传不解释。私货不污染契约，避免「事实标准」绑架主版本。

二 / Roles

角色与拓扑：只有托管模式，明确拒绝无状态网关

问题裁定
谁是 IR 与台账的所有者系统，唯一写者。外部 Agent 永不直接写 IR / 台账；一切变更经 Patch 提交给应用器（§1.3 v0.4 两阶段模型照常执行）。外部持有的只是公共投影（PublicIR）。
要不要提供无状态网关模式
（宿主自带 IR，系统只回补丁）		不提供。该模式要求宿主侧实现应用器与台账，单一写者被破坏，审计、回归保护、学习血缘全部失效——恰是 v0.2 评审用血泪换来的不变式。对外只保留托管模式，明确写入非目标，不留模糊地带。
外部 Agent 的三种身份① 能力消费者（generate / iterate / score / render）；② 事件源（托管会话内推对话轮，接收改进建议）；③ 治理请求方（保护类申请、新模型卡申请——都只是「请求」，批准权永在外部主体之外，见 §9）。

三 / Capabilities

能力目录：9 项能力，先协商后调用

能力说明同步性就绪阶段
discovery.v1能力协商、IR/Patch Schema 获取、受支持模型卡清单（含复现层级标注）同步P0a
generate.v1从零生成：对话/材料 → IR + 渲染 + 证据包（异步任务）异步P0a

score.v1L1 静态分（默认）+ L2 成对裁决（需已确认 rubric）；L3 深度模式按连接器预算开关，默认 off同步P0a
iterate.v1种子反解 + 补丁式改进（输入：种子文本或父 IR）；回归保护自动生效异步P0b

modelcard.request.v1申请登记新目标模型（触发登记与基准子集实测流程，非直写）同步P0b

四 / Bindings

绑定协议：逻辑契约与传输解耦，一契约两绑定

4.2 绑定 B：MCP（Agent 原生通道）

MCP 工具与 HTTP 资源一一对应、共用同一套 DTO 与错误码：工具名即能力的协议化拼写——pg_generate、pg_iterate、pg_task_status、pg_task_cancel、pg_rubric_confirm、pg_score、pg_render、pg_session_open、pg_turn_record、pg_patch_apply、pg_capabilities。MCP 绑定由 MCP 适配器实现，逻辑与 HTTP 完全等价——两个适配器跑同一 TCK，保证行为无分叉。

4.3 契约测试套件（TCK）：接入的唯一硬门

TCK 是本规范的可执行形式：一组对任意客户端/适配器都可判定的用例（含 §11 的全部验收项 + v0.4 的非法 Patch 样本经 API 通道复放）。新连接器注册为 production 的前置条件 = 沙箱租户上 TCK 全绿。TCK 本身随规范冻结，版本化维护——这使「接口质量」从评审时的约定变成每次接入时的机械检查。

五 / Contracts

数据契约：公共信封与核心 DTO

5.1 公共信封（一切请求的强制外壳）

{
  "api_version": "1",                  // 主版本，整数递增；不兼容变更必须升主版本
  "request_id": "uuid",               // 客户端生成，全链路追踪与去重
  "idempotency_key": "sha256:...",    // 语义与 Patch 幂等键一致：同键重放返回首次结果
  "connector_id": "conn-0007",        // 注册时分配；token 反查校验
  "tenant_id": "t-001",               // 租户隔离边界
  "budget_hint": {...},               // 可选：本次调用的预算意愿，受连接器上限裁剪
  "extensions": { "x-*": ... }        // 可选：私有扩展，只透传不解释
}

5.2 核心 DTO（与 v0.4 对象一一对应）

DTO内容要点继承自
TaskRequestop（generate/iterate）、对话窗口（轮文本 + content_hash）、材料列表（引用 + content_hash）、target_model、rubric_policy（默认 draft_then_confirm）、iterate 模式二选一：seed_text 或 parent_ir_idv0.4 §1 / §2

六 / Task Model

异步任务模型：生成与迭代是任务，评分渲染是调用

回调采用 at-least-once + 客户端按 event_id 去重；事件信封：{event, api_version, event_id, occurred_at, signature, data}，签名 hmac-sha256，计算基础为 RFC 8785 canonical JSON——与 IR checksum 同一序列化标准，验证代码可共用。轮询兜底 SLA：任务最长存活 15 分钟，超时自动 failed 并退回降级路径（返回已完成层级的部分结果 + 层级标注，与 v0.2 §5.3 一致）。

七 / Online Events

在线事件模型：复用四元组，host 永不直接改 IR

  1. 开会话：host 调 POST /v1/sessions（绑定 ir_id）→ session_id, session_epoch=0。
  2. 推轮次：host 调 events 推 turn.recorded（轮文本 + 材料引用 + content_hash）。材料 hash 是 v0.4 §5.1 的 input_version 机制在外部通道的形态：同名替换文件照样触发失效。
  3. 语义分类在系统侧：按 v0.4 §6.1 分类——寒暄/进展不作废；材料/目标/约束/纠正进入去抖窗口；不确定保守作废。host 不需要实现语义判定，也不被允许覆盖它。
  4. 建议回调：系统经 suggestion.proposed 推送 Suggestion DTO（补丁 + 四元组 + 证据）。饥饿监控按连接器维度统计（作废率告警口径同 §6.2）。
  5. 确认应用：host 调 patches 提交确认 → 系统内走应用器，CAS 四元组任一不符即拒绝（E_BASE_DRIFT / 语义过期），host 收到精确错误码后自行决定是否重新排队。host 全程接触不到 IR 写路径。
  6. 效果归因：应用后的归因窗口、失败签名滞回判定全部在系统侧，host 只通过 governance.read.v1 读结果——保证 P1 的在线指标口径（两率分报、误回滚=0）不被外部实现稀释。

八 / Errors

错误模型：一套 E_* 走天下

error_codeHTTP说明
E_AUTH / E_SCOPE401 / 403认证失败 / 能力未授权（新增，传输层）
E_RATE_LIMIT / E_BUDGET_EXCEEDED429限流 / 预算耗尽（含 Retry-After；预算口径 = v0.4 §5.4 连接器维度限额）
E_SCHEMA_INVALID422信封或载荷未过校验（复用 v0.4）
E_BASE_DRIFT409四元组 CAS 不符（复用；在线场景含语义过期语义）
E_PROTECT_ENACTED / E_PROTECT_REWRITE / E_PROTECT_MOVE / E_PROTECT_ANCESTOR / E_PROTECT_FIELD403保护类只读与授权通道（复用 v0.4 §3 全集）
E_LOC_RETIRED / E_INDEX_FORBIDDEN / E_ROOT_FORBIDDEN / E_ID_SYNTAX / E_FIELD_UNKNOWN / E_*_TARGET / E_DELETE_NONEMPTY422应用器错误码全集经 API 透传（复用 v0.4 §1.4，含 @ op[N] 定位）
E_UNSUPPORTED_OP501能力协商未声明该 op 却被调用（新增）
E_IDEM_REPLAY200幂等命中：返回首次结果而非错误（复用；显式写进契约防客户端误判）

设计理由：外部 Agent 调试提示词问题时看到的错误语义，与系统内部应用器看到的完全同源——不存在「API 层错误码」与「核心错误码」两套需要对照翻译的体系。错误响应统一信封：{error_code, message, detail{op_index?, stage?}, request_id}。

九 / Security

安全与治理：连接器是第 11 类不可信输入源

  • 不可信载荷：连接器带来的一切内容（对话、材料、种子文本）在进入 M1 前按不可信数据处理（v0.4 §5.3 边界自动延伸），存储型注入测试用例集增加「经连接器通道」一组。
  • 权限矩阵：连接器可做——提交任务、推事件、确认应用建议、发起治理请求；连接器永不能——写台账、enact 保护类、批准 ProtectionChange、直写模型卡、跳过 rubric 确认。三权模型（v0.3 §3）对外部主体天然关闭批准权。
  • 租户隔离：connector_id 绑定 tenant，token 只能触达本租户资源；跨租户调用返回 E_SCOPE 并入审计。
  • 审计入链：连接器注册、scope 变更、全部调用与治理请求写入哈希链台账（v0.4 §6.3），防篡改验证覆盖连接器事件类。
  • 预算与降级：每连接器独立限额（任务数/token/深度评估开关）；超限返回 E_BUDGET_EXCEEDED 而非静默排队，防止外部调用方把预算问题误读为系统故障。
  • token 治理：token 引用密钥库（vault），支持轮换与吊销；吊销即时生效并产生审计事件。

十 / Config

配置项参考：一个新 Agent = 一份配置 + TCK 通过

connectors:
  - id: host-agent-alpha                 # 注册时分配，全局唯一
    tenant_id: t-001
    enabled: true
    auth:
      type: bearer                       # bearer | mutual_tls
      token_ref: vault://conn/t-001/host-alpha     # 引用而非内联密钥
      rotation_days: 90
    scopes: [discovery.v1, generate.v1, render.v1, score.v1, iterate.v1, events.v1]
    budget:
      max_tasks_per_day: 200
      max_tokens_per_task: "250k"
      l3_deep_eval: false                 # 默认关闭（继承 v0.2 §5.3 深度模式口径）
    callbacks:
      enabled: true
      url: https://host.example/hooks/promptgen
      secret_ref: vault://conn/t-001/webhook-hmac
      events: [task.completed, task.failed, suggestion.proposed]
      retry: {policy: exponential, max_attempts: 5, backoff_base: "2s"}
    timeouts:
      sync_call: "10s"
      task_max_lifetime: "15m"
    sandbox: false                        # 沙箱租户上 TCK 通过后方可置 false

十一 / Onboarding

接入流程与验收清单

  1. 注册：管理员创建连接器（租户、scopes、token、预算、回调），初始 sandbox: true、沙箱租户 + Mock 绑定（可离线跑通全流程，与评测规范的 Mock 模式同源）。
  2. 协商：客户端拉取 capabilities + schema + model-cards，确定工作集。
  3. 沙箱试跑：在沙箱租户完成全部目标能力的调用与回调验证。
  4. TCK 全绿：跑契约测试套件（下表），结果入审计。
  5. 转生产：管理员将 sandbox 置 false、提升配额——全程零核心代码变更。
TCK 验收项必须证明
宽容读者注入未知字段（含 x- 扩展）不报错、不改变行为
幂等重放同 idempotency_key 重放返回首次结果（E_IDEM_REPLAY → 200）
回调验签与去重错误签名被拒；重复 event_id 被正确去重；重试退避生效
预算超限行为收到 429 + Retry-After，而非静默排队或假成功
取消幂等重复取消无害；取消后无副作用提交
rubric 锚点路径不确认 rubric 任务不推进；确认动作留痕
错误码全样本v0.4 §1.4 全部 E_* 经 API 通道透传且带 @ op[N] 定位
复现层级透传EvalEvidence 携带 T1/T2/T3 标签，不得被适配器抹除
保护类不可越权protection-request 只产生 proposed；enact 尝试返回 E_SCOPE
租户越界跨租户资源访问全部返回 E_SCOPE 且入审计

十二 / Consistency

一致性核查与阶段映射

核查项结论
单一写者不变式保持——host 无 IR 写路径，一切经应用器；无状态网关模式被明确排除并写入非目标
CAS 四元组与幂等原样复用；连接器 idempotency_key 与 Patch 幂等键同一语义与同一实现
rubric 人工锚点（v0.2 §5.2）API 通道不绕过：rubric_pending 状态 + 确认端点 + 超时取消，确认动作入审计
保护类三权（v0.3 §3 / v0.4 §3）连接器只有请求权，无批准权；enact / approve 全部拒绝并计 E_SCOPE
声明门禁与层级（v0.4 §4）对外证据强制携带 reproduction_tier；TCK 含「标签不得抹除」用例——连接器不会成为声明漂移的后门
范围防回涨（v0.2 §2）能力面 = MVP 既有能力；消息编排、工具 schema 等非目标不因连接器而重启
