提示词生成器的工作原理

从 WorkBuddy 的原生组装机制，到 GitHub 上四类开源实现，再到模型内部的概率机制——把"写好一段提示词"拆成可被工程复现的六个环节。

系统拆解 4 个部分 7 个开源项目 2026-10-24

导读：所有提示词生成器，都在解同一个方程

表面上看，提示词生成器五花八门：有的是网页按钮，有的是编程框架，有的是语法编译器。但它们试图解决的其实是同一个问题——人的意图是稀疏的、缺省的、情绪化的；模型的输入必须是稠密的、无歧义的、可条件化的。生成器就是这个转换层。

把它写成一句话：给定一个模糊的意图 I 和一个目标模型 M，生成器要产出一段文本（或一段程序、或一组权重）P，使得 M 在 P 的条件下的输出分布，尽可能集中在人真正想要的结果 y* 上。

这个定义里藏着四个变量，也就分出了四种技术路线：P 从哪里来（模板 / 搜索 / 编译 / 训练）、怎么知道 P 变好了（人看 / LLM 裁判 / 客观指标 / 语法合法性）、优化发生在什么时候（写时 / 运行时 / 训练时）、以及保证有多硬（概率性 / 确定性）。后文的四部分，就是围绕这四个变量展开的。

Method note
关于本文的证据分级。第一部分中，凡涉及 WorkBuddy 的界面与能力边界，均以官方文档公开描述为准；凡涉及"模型侧如何拼装上下文"，属于从可观察行为与公开的 Skill / 记忆 / 专家机制反推的架构归纳，用于说明设计范式，不代表具体实现细节。第二部分全部基于各项目仓库与官方文档的一手内容。第四部分为当前主流 Transformer 架构的公开共识。

一 / Part One

WorkBuddy 的原生提示词生成机制

先纠正一个常见误解：WorkBuddy 并没有一个"输入需求、吐出提示词"的独立按钮。它的原生能力是把用户的自然语言直接当作可执行的任务指令——也就是说，"生成提示词"这件事被内化成了任务创建、上下文装配与执行编排的一部分。

这套机制可以拆成三层：最外层是面向人的结构化引导（把一句话需求补成任务简报），中间层是可编程的提示词载体（Skill / 专家包），最内层是面向模型的上下文组装（每一轮推理前把离散信息源拼成一次请求）。三层叠加，才构成完整的"原生生成器"。

1.1 三层生成模型：静态模板 → 半动态 Skill → 动态编排

层载体生成物变化频率谁来验收
L1 模板层 创建任务页的场景模板（日常办公 / 代码开发 / 设计创意） 一段带占位符的提示词骨架 静态，随产品迭代 人（点选即用）
L2 载体层 Skill（SKILL.md + references/）、专家包、连接器 可复用、可版本化的提示词程序 半动态，用户可编写 人 + 运行结果
L3 装配层 运行时上下文组装管线 一次真实的模型请求 每一轮都变 模型（执行）+ 人（结果区）
L1：模板层——用"预览态"降低试错成本

官方文档里有一个值得注意的交互细节：鼠标悬停模板时，输入框会以灰色预览文案显示模板内容；若输入框已有文字，预览接在末尾、原文保持黑色；移开或失焦即清除；灰字不进入草稿、不进撤销栈、不会被发送，只有点击才真正填入。

这个设计不是 UI 洁癖，而是把"提示词的成本"从"要不要用"降到了"看一眼"。传统提示词库的失败点在于：用户不知道模板长什么样，于是不敢点；点了又怕覆盖自己写的东西。灰度预览同时解决了"信息不对称"和"操作不可逆"两个阻力——这是提示词产品化里最容易被忽略的一环。

L2：载体层——Skill 就是 Markdown 写成的提示词生成器

Skill 机制的本质，是把提示词从"一次性字符串"升级为"可加载的模块"：一个目录、一份 SKILL.md 定义角色与工作流、若干 references/ 存放按需加载的参考资料。社区里已经有人用这套机制搭出完整的提示词生成 Agent——流程是「信息收集 → 加载模型特性表 → 按目标模型生成 → 格式化输出」。

这里的关键机制叫渐进式披露（progressive disclosure）：模型的上下文里常驻的只有一句"这个技能存在、什么时候用"，全文与参考资料只在触发时才载入。类比到提示词生成器上，意味着你可以在 references/model-cards.md 里为每个模型写一份"提示词偏好卡"（比如某个模型对 XML 标签敏感、某个模型对超长系统提示衰减更快），生成时按需取用，而不是把所有模型的知识都塞进一次请求。

更进一步，专家包把"角色人格 + 方法论 + 输出规范"打包成一个可切换的身份层。从提示词角度看，这等价于给系统提示词换了一套高优先级的先验——比在用户消息里写"你是一位资深分析师"要稳固得多，因为它不在对话历史里、不会被后续轮次稀释。

1.2 上下文组装管线：一次请求里的六个层

"原生提示词生成"真正发生的地方，是每一轮推理前的组装时刻。把可观察到的信息源按稳定性排序，会得到一个从"几乎不变"到"每轮都变"的堆栈：

这六层的排布遵循三条隐性规则，值得单独拎出来说：

  1. 稳定性与优先级同向。越不容易变的内容放越前、给越高权重。这样模型的"行为基线"不会被单轮输入轻易推翻，也避免了用户消息里的一句话覆盖掉全部安全边界。
  2. 按需加载而非全量常驻。Skill 的全文、参考资料、模型特性表都不在一开始就进入上下文，只在触发时引入。这既省 token，也减少注意力稀释（见第四部分 4.4）。
  3. 数据与指令显式分区。附件、引用文件、页面抓取内容都被包在明确的边界里，而不是和指令混在一段自然语言中。这是缓解"提示词注入"的结构性手段，也顺带提升了模型对指令的遵循度。

1.3 设计思路：把"提示词"重新定义为"任务契约"

看官方文档的措辞会发现一个倾向：它几乎不谈"提示词技巧"，而反复谈目标、输入、输出格式、约束条件这四件事。文档明确建议用户在任务描述里补充：目标是什么、输入是什么、希望得到什么格式、有哪些约束（风格、字数、截止时间）。这四要素其实就是一份最小可执行契约。

这个取向背后有一条重要判断：Agent 场景下，提示词的作用从"描述任务"变成了"约束行为"。对话式 AI 的提示词只需要说清"写什么"，而 Agent 的提示词必须说清"允许做什么、不允许做什么、做到什么程度算完成、失败了怎么收场"。因为 Agent 会真的动文件、真的发请求，模糊的指令会变成不可逆的副作用。

由此衍生出四个设计要点：

设计要点具体做法解决的问题
模式即策略 提供"只回答 / 直接执行 / 先规划再执行"三档。选择模式本身就是在给提示词附加执行策略——Plan 模式相当于强制模型先输出方案、等人确认后才允许产生副作用。 不可逆操作被前置拦截
上下文优先于形容词 用 @ 引用文件、贴截图、上传附件、指定工作空间，让模型"看材料"而不是"猜"。文档把"输入是什么"列为必填项。 幻觉与凭空发挥
验收标准显式化 把"什么算做完"写进任务描述，而不是留给模型自己判断。结果区提供产物、文件、变更三个视角供人复核。 交付物看似完成实则跑偏
能力可组合 专家（角色与方法论）、技能（流程与脚本）、连接器（外部数据与动作）、资料库（私有知识）四类扩展互相正交，按任务拼装。 一个巨型提示词无法维护

顺带一提，业界教程把这种契约式写法归纳成 BRIEF 五段式，可以拿来当检查清单：Bounded outcome（一个有终点的交付物）、References（权威来源，精确到文件与日期）、Instructions（必须包含的内容与格式）、Exclusions（不许做的事）、Final checks（交付前怎么自检）。它和 WorkBuddy 文档的四要素基本同构，多出来的是"排除项"和"自检"——这两项在 Agent 场景里恰恰最关键。

1.4 取舍与边界

这套设计的代价也很清楚。其一，它把负担部分转移给了用户：不写清目标和约束，效果就会明显下降——因为系统选择了"不替用户编造需求"，这在长周期任务上是正确的，在随手一问时就显得啰嗦。其二，模板层天然滞后于模型演进，模板里固化的写法可能对新模型已经过时。其三，多 Skill 并存时存在触发歧义：两个技能都声称适用，装配层只能靠描述文本的匹配度取舍，这是当前所有 Skill 体系的共同软肋。

二 / Part Two

GitHub 上的代表性开源实现

下面七个项目，恰好覆盖了四条互不重叠的技术路线。我按"提示词从哪里来"把它们分成三族（外加一族特殊的权重层方案），每一族先讲共同架构，再逐项拆到实现细节。

2.0 三个技术家族

2.1 家族 A：模板与范式驱动

这一族的共同特征是没有反馈回路：提示词的质量在上游由人的方法论决定，下游只做结构校验，不做效果评估。优点是零额外调用成本、完全可解释、可版本化；缺点是质量天花板就是作者的水平。

langgptai/LangGPT 结构化提示词范式 家族 A
定位
把提示词设计类比为编程语言：有模块、有变量、有命令、有初始化，因此可复用、可维护、可协作。
架构
DSL 就是 Markdown。核心骨架为 Role → Profile → Goal → Skills → Rules → Workflow → Initialization，可选 Commands（斜杠命令）与 Reminder（长对话中反复锚定角色）。
关键机制
它的"生成器"其实是模型本身。因为这套结构在中文语料里传播极广、已进入主流模型的训练分布，只需说"用 LangGPT 方式写一个提示词"即可触发。这本身是一个值得注意的现象：一种提示词范式被广泛采用后，会反向沉淀为模型的先验知识。
实现细节
较新版本把 Goal 细化为三件套：Outcome（要交付什么）、Done Criteria（怎样算做好）、Non-Goals（明确不做什么）。前者对治"目标漂移"，后者对治"范围膨胀"——这是从"角色扮演模板"向"工程契约"演进的关键一步。
学术化
arXiv:2402.16929 将其形式化为"面向 LLM 的结构化可复用提示词设计框架"，逐项对应编程语言要素。生态里还有 PromptVer（提示词语义化版本）、Minstrel（多 Agent 自动生成提示词）。
局限
无自动评估，好坏全凭人判；模板套壳极易产出"形式完整、内容空洞"的提示词——字段都填了，但没有一条是可执行的约束。
promptslab/Promptify 任务模板引擎 家族 A
定位
自我描述为"LLM 版 scikit-learn"：把 NLP 任务抽象成一致的类接口，用两三行代码拿到结构化结果。
架构
四层：Task 基类 → 任务子类（NER / Classify / QA / Summarize / ExtractRelations / GenerateSQL …）→ Pydantic 输出 schema → LiteLLM 统一后端（一套代码切 100+ provider）。
关键机制
模板装配：任务指令 + 领域提示（domain="medical"）+ few-shot 示例 + schema 说明，拼成最终提示词。所以它属于"模板族"——用任务类型索引到对应模板，而非搜索最优措辞。
实现细节
两个亮点。一是 safe parser：对不支持原生结构化输出的 provider，用 JSON 补全兜底而不是 eval()，安全性上比早期实现更严谨。二是把评估做进库：evaluate(task, dataset, metrics=[...]) 直接算 precision / recall / F1，让"提示词有没有变好"第一次有了可跑的答案。
局限
v3 已收敛为"任务引擎"，提示词优化不是主路径；模板与任务强绑定，超出内置任务类型就要自己写 Task + schema。

2.2 家族 B：生成—评估—选择

这一族引入了反馈回路，因此有了"自动变好"的可能。它们的共同架构是四段：候选生成 → 用例批跑 → 信号评估 → 择优/迭代。差别在于"信号"从哪来（LLM 裁判 / 客观指标 / 人工标注）以及"搜索"怎么走（锦标赛 / 坐标上升 / 贝叶斯优化 / 进化）。

mshumer/gpt-prompt-engineer 锦标赛式提示词搜索 家族 B
定位
作者的原话是"提示词工程像炼金术，只能靠试"——这个项目把"试"自动化成一场锦标赛。
架构
单文件 notebook，一个入口函数 generate_optimal_prompt(description, test_cases, number_of_prompts)，内部四个阶段串行。
流程
  1. 生成：用元提示词让强模型就同一用例描述产出 N 个风格不同的候选提示词（N 建议从 10 起，因为成本随 N 线性上涨）。
  2. 批跑：每个候选 × 每个测试用例各调一次模型，收集输出。生成与评判用强模型、被测生成用便宜模型，是它控制成本的关键配置。
  3. 成对裁判：把同一用例下两个候选的输出交给裁判模型，判定 A 更好 / B 更好 / 平局。
  4. Elo 排名：每个候选初始 1200 分，按每场对局结果更新，最终输出降序表格。
为什么是 Elo 而不是打分
这是整个设计里最巧妙的一步。绝对打分（"给这段输出打 1–10 分"）在不同批次间不可比、且模型倾向于给中庸分；相对比较只要求裁判回答"哪个更好"，判断更稳、方差更小，还能顺带解决"没有标准答案"的开放性任务。代价是只能得到序关系，不能得到绝对质量。
变体
分类版改用 ground truth 直接算准确率，绕过 LLM 裁判；Claude 版支持多输入变量并自动生成测试用例；还有 Opus→Haiku 蒸馏版，用强模型产出高质量示例来引导小模型。
局限
单一裁判存在同族偏好（self-preference bias）；用例少于十条时 Elo 排名不稳；A/B 顺序需要随机化以抑制位置偏差；最终选出的提示词只在被测模型上验证过，跨模型不保证迁移。
linshenkx/prompt-optimizer 产品化的提示词资产工作台 家族 B
定位
把提示词当作可版本化的资产来管理：写、优、测、评、存、复用，形成闭环。
架构
同一套核心跑在五种形态上——Web、桌面端、Chrome 扩展、Docker、MCP Server。纯客户端处理，模型请求直连 provider，不经中间服务器（既省成本也避免密钥外流）。Provider 适配层覆盖 OpenAI / Gemini / DeepSeek / Grok / 智谱 / SiliconFlow / MiniMax 等。
关键机制
模板 + 元提示词驱动。优化动作分三种：系统提示词优化、用户提示词优化、迭代优化（对已成熟的提示词按具体诉求改进）。三者用的是不同的元提示词模板——这区分很重要，因为系统提示词要求"稳定、可长期生效、覆盖边界"，用户提示词要求"具体、一次性、带材料"，两者的优化目标根本不同。
评估设计
提供四档：结构分析（把提示词拆成意图/约束/输出要求，指出缺项）、单结果评估、多结果对比评估、以及评估驱动的智能重写（用评估结论反过来改提示词）。这一层把它和纯模板工具区分开了——它有反馈回路。
工程细节
上下文变量管理与批量替换、多轮对话测试、Function Calling 测试；收藏夹带版本历史与可复现示例；MCP 暴露 optimize-user-prompt / optimize-system-prompt / iterate-prompt 三个工具，可被其他 AI 应用直接调用。图像侧另有 T2I/I2I/多图模式，把一句话扩写成可控的视觉提示词。
局限
优化质量的上限就是所选基座模型的提示词写作能力；评估仍是 LLM 主观判断而非客观指标，同一提示词换裁判模型结论可能翻转。
stanfordnlp/dspy 把提示词当参数来编译 家族 B / C 跨界
定位
不做"提示词生成"，做"提示词编译"。人只声明输入输出语义与评价指标，具体的措辞与示例由优化器搜出来。
三层抽象
Signature：声明 question -> answer 或类形式，docstring 即初始指令；
Module：Predict / ChainOfThought / ReAct / ProgramOfThought，把签名包成可组合单元，每个模块持有自己的 instructions 与 demos；
Adapter：把签名 + 示例渲染成目标模型需要的具体格式（chat / JSON / XML）。
优化器谱系
这是它最值得细看的部分，几代方法对应几种搜索策略：
  • LabeledFewShot：直接抽 k 个标注样本当示例。基线。
  • BootstrapFewShot：让教师程序跑训练集，只保留通过 metric 的轨迹，把"输入 → 成功推理过程"作为示例。妙处是不用人写思维链，思维链由模型自己跑出来再筛选。
  • BootstrapFewShotWithRandomSearch：多次自举 + 随机搜索示例组合。
  • COPRO：只动指令，坐标上升——每轮针对一处生成候选措辞、评分、保留更优者。
  • MIPROv2：同时优化指令与示例。先用数据集摘要 + 程序代码 + 提示让强模型"有依据地"提出指令候选，再用贝叶斯优化（TPE）在组合空间里搜，auto 参数控制预算档位。
  • GEPA：反思式进化。关键创新是 metric 可以返回自然语言反馈（Prediction(score=..., feedback="...")），反思模型读到"为什么失败"再改写指令；配合 Pareto 采样保留多样候选，避免早熟收敛。
实现细节
优化产物是可序列化的状态文件（每个 predictor 的指令与示例），optimized.save("x.json") 存盘；训练集供反思、验证集供选优，官方明确建议另留测试集，否则报告的是过拟合后的分数。
关键洞察
同一段程序在不同模型上会被优化成不同的提示词——这从工程上证明了"提示词没有普适最优解，只有针对特定模型的最优解"。官方举的例子是优化后的小模型得分超过未优化的大模型。
局限
需要训练集与可计算的 metric，冷启动门槛高；一次编译的调用成本不低；metric 设计得不好，优化器会精准地优化错的东西。

家族 B 还有一个极端的变体值得单列：microsoft/LMOps 的 Promptist。它不生成文本，而是训练一个改写器——两阶段，先用筛选出的高质量样本做监督微调，再用强化学习（PPO）继续优化，奖励来自生成图像与提示词的 CLIP 相似度，并用 KL 惩罚约束改写器不要偏离原意太远。使用时在输入后加上 Rephrase: 触发，beam search 出多个候选。它的意义在于揭示了另一种可能：提示词优化可以被编译进权重，运行时零额外开销。代价是完全绑定特定生成模型与偏好，不可解释、不可迁移。学术上的源头则是 AutoPrompt 一类工作——用梯度信号引导离散 token 的搜索（hotflip 式候选替换 + beam search），把"哪几个词最有效"变成一个可优化的组合问题。

2.3 家族 C：声明式编译与约束解码

这一族换了问题：不再问"怎么写出更好的提示词"，而问"怎么让提示词变成带保证的程序"。它们把提示词从"一段希望模型照做的文字"降级为"一个可编译、可校验、可约束的中间产物"。

guidance-ai/guidance 交织控制与生成的提示词程序 家族 C
定位
把提示词写成 Python 程序：控制流（条件、循环、函数调用）与生成动作在同一个流程里交织，而不是"先拼字符串再一次性发出去"。
核心 API
gen() 生成、select() 从枚举里选、regex= 正则约束、json(schema=Pydantic) 结构化、@guidance 自定义可组合函数、capture() 捕获、one_or_more() 重复。模型对象不可变（lm += ... 返回副本），因此可以分支、可以回滚——这是它能做搜索式生成的前提。
约束怎么实现
正则 / 上下文无关文法 / JSON Schema 都被编译成状态机。解码每一步，把当前状态下非法的 token 的 logits 置为负无穷，只在合法集合上做 softmax。所以格式不是"大概率正确"，而是结构性不可能出错。
两个精巧机制
Token fast-forwarding：语法已经确定的 token 不必让模型生成，直接插入并跳过前向计算。生成 HTML 时，一旦模型吐出 </，后面的标签名往往可以补齐——省下的是真实的 GPU 时间。
Token healing：BPE 分词会在提示词末尾留下"半截 token"，导致模型对第一个生成 token 的分布产生偏差。它的做法是回退到 token 边界重新生成，再拼接回去，消除这个系统性误差。
工程化
@guidance(stateless=True) 把函数编译成可组合的语法片段；Mock 模型配合 grammar.match() 可以完全离线验证语法，调试约束时不烧 API 额度。
局限
硬约束需要能访问 logits（Transformers / llama.cpp 等本地后端）；对只能拿到文本的闭源 API 只能降级为"强制前缀"等软手段。语法写得再严也只能保证合法，不能保证正确——一个语法完美的 JSON 可以是语义垃圾。
BoundaryML/baml 面向 LLM 的编程语言 家族 C
定位
不满足于做模板库，直接造了一门语言：有 AST、有类型推断、有中间表示、有字节码虚拟机（BEX VM）、有栈预算与类型化 panic。把"调模型"当成一等语言特性。
语言构成
class 声明输出 schema（字段可带 @description / @alias 注解）；function 声明签名 + client + prompt 模板；test 块内嵌测试用例。.baml 文件是唯一真相源。
schema-aligned parsing
这个名字涵盖三件常被混淆的事：
① 把类型写进提示词——模板里的 {{ ctx.output_format }} 会自动把返回类型渲染成模型可读的 schema 说明，类型改了提示词跟着变，不会漂移；
② 容错解析——缺引号、多余前后缀、字段别名、流式半截 JSON，都在客户端修复；
③ 错误回灌重试——解析失败时把具体错误信息喂回模型重试，而不是盲目重发。
codegen
baml generate 产出 baml_client，把函数变成宿主语言的强类型方法（Python / TypeScript / Go / Ruby 等），返回值是真实的类实例而不是裸字符串。IDE 里有补全，编译期就能发现字段名写错。
与传统写法的差别
手写 f-string 拼提示词时，类型定义、提示词文本、解析逻辑是三份各自演化的副本，改一处必然漏两处。BAML 把它们合并成一个声明，让"提示词与 schema 的一致性"从人的纪律变成编译器的职责。
局限
引入新语言与构建步骤，团队要付学习成本；复杂业务控制流仍然要回到宿主语言，跨语言边界有胶水成本。

把 DSPy 放到这张图里看会更清楚：它的 Signature/Module 是 C 家族的思路（声明意图、由编译器决定措辞），它的 Optimizer 是 B 家族的思路（用指标搜索）。所以它实际上是用 B 的方法去实现 C 的理想——这也是为什么它能同时被当作"提示词优化器"和"提示词编程框架"使用。

三 / Part Three

横向对比：共性、差异与选型

3.1 五条共性原理

把七个项目摊平来看，它们在方法论上的重合度比表面差异大得多。

共性内涵在各方案中的体现
① 槽位补全 把"角色 / 任务 / 材料 / 格式 / 约束 / 示例"六个槽位填满，提示词的可用性就跃升一个台阶。 LangGPT 的模板就是六个槽位的具名化；WorkBuddy 文档的四要素是同一件事的收敛版；Promptify 用 schema 补"格式"槽。
② 条件分布塑形 所有生成动作的物理本质，都是把 p(y|P) 从弥散推向尖锐。 越具体的约束 → 分布越尖；越多的示例 → 分布越像目标模式。第四部分会展开机制。
③ 生成与评估分离 只要系统能判断"哪个更好"，它就能自动改进；不能判断，就只能靠人。 gpt-prompt-engineer 用 LLM 裁判，DSPy 用 metric，Promptify 用 P/R/F1，guidance 用语法合法性——四种"判断"，四种自动化上限。
④ 相对优于绝对 在缺乏标准答案时，成对比较比绝对打分更稳。 Elo 锦标赛、Pareto 前沿采样、A/B 对比评估，本质都在把"打分"降解为"排序"。
⑤ 结构即约束 声明式的结构（类型、语法、模板）比自然语言的祈使句更可靠。 BAML 的 class、guidance 的文法、DSPy 的 Signature，都在用"结构"替代"请求"。

3.2 差异矩阵

真正的分野在四个维度上：优化对象、验收信号、时机、保证强度。

3.3 选型建议

你的处境推荐理由
个人日常使用，一次性任务 直接写任务简报（WorkBuddy 模式） 所有自动化方案的前期投入都大于收益；把目标/输入/格式/约束说清就是最优解。
要给团队沉淀一套可复用提示词 LangGPT 式结构化模板 可读、可评审、可 diff。先解决"能不能维护"，再谈"能不能更优"。
提示词要嵌入产品，输出必须被程序消费 BAML 或 guidance 前者胜在类型安全与多语言客户端，后者胜在本地模型上的极致控制与 token 节省。
有几百条标注数据，想把准确率再提 10 个点 DSPy（先 BootstrapFewShot，再 MIPROv2 / GEPA） 唯一能系统利用数据的方案；但要先确认 metric 真的衡量了你想要的东西。
没有标注数据，只有一堆真实输入样本 gpt-prompt-engineer 式锦标赛 用相对比较绕过"没有标准答案"，成本可控，当天能出结果。
要给非技术同事用 prompt-optimizer 类产品 有界面、有模板、有对比评估，学习成本最低；但要接受评估偏主观。
多模型混用，同一提示词要在各家都跑通 结构化模板 + 每模型特性卡（Skill + references） 因为不存在普适最优提示词，只能把"模型差异"做成可替换的知识模块。

3.4 三条共同边界

第一，生成器不能创造模型没有的能力。所有方案优化的是"把已有能力引导到正确位置"，不是"注入知识"。当任务需要模型训练数据里没有的事实时，再精巧的提示词也只能让它更流畅地编造。

第二，评估信号的天花板就是优化效果的天花板。DSPy 官方文档里那句提醒值得抄在任何提示词工程规范的第一页：优化器会精准地优化你写的 metric，包括你写错的部分。用 LLM 当裁判时同理——裁判的偏好会被继承，包括它的长度偏好、格式偏好和同族偏好。

第三，优化与过拟合只隔一层验证集。搜索空间越大（候选越多、迭代越久），在有限用例上过拟合的风险越高。凡是带自动优化的方案，都必须留一份既没进训练集也没进验证集的测试集，否则报告出来的提升很可能只是记住了样本。

四 / Part Four

AI 理解提示词的基本原理

前面三部分讲的是"怎么造提示词"。这一部分换个方向：提示词进入模型之后，究竟发生了什么？理解了这条流水线，前面所有的经验法则就不再是玄学，而是一条条可以推导的结论。

4.1 五个阶段：从字符串到概率分布

逐段说明其中容易被忽略的三处：

分词决定了模型"看得见什么粒度"。BPE 把文本切成子词单元，中文常是一字一 token 或两字一 token，数字和代码会被切得很碎。这解释了两件日常现象：为什么"写 800 字"经常不准（模型数的是 token 不是字，而中文字数与 token 数的换算比例并不固定），以及为什么罕见专有名词容易出错（低频词被切成碎片，模型难以形成稳定表示）。

注意力是"软检索"，不是"硬查表"。每个位置的向量会被投影成 Query、Key、Value 三份；用当前 Query 与所有前序 Key 做点积得到相关性权重，再对 Value 加权求和。这意味着模型对提示词的每一处内容都只分配一个权重，而不是精确读取。所有 token 分享固定的注意力预算，一段内容占得多，别处就占得少——这就是"注意力稀释"的物理来源。

层数带来抽象层级。浅层偏向词法与局部搭配，深层偏向语义角色与任务意图。所以同一句话在不同深度被"理解"成不同的东西，而提示词的作用是同时影响每一层。

4.2 核心视角：提示词是"条件"，不是"命令"

模型做的事情只有一件：在给定前文 x<t 的条件下，计算下一个 token 的概率分布 p(xt | x<t)，采样一个，接回序列，重复。
所以提示词的全部作用可以写成一句话：把条件分布从"泛泛而谈"推向"你想要的区域"。

这个视角能解释一件反直觉的事：为什么模型"知道答案却答不对"。知识存在于参数里（能力集合没变），但采样路径被前文的措辞、格式、语气引导到了别处（分布形状变了）。同一个问题换个问法就对，正是分布被重塑的证据。

4.3 把经验法则翻译成机制

常见写法机制解释什么时候会失效
设定角色 / 人格 把分布移向该角色语料所在的"语域"（register）：用词、句式、关注点、默认假设一起偏移。它选择的是风格与视角，不是知识库。 角色与任务无关时纯属噪声；角色越具体，越容易挤占注意力而遮蔽任务本身。
给示例（few-shot） 上下文里形成的模式会被"归纳头"（induction heads）捕捉并复制：模型识别出"输入长这样→输出长那样"的结构，然后套用。示例同时隐式规定了输出长度、粒度与格式。 示例与真实输入分布不一致时，模型会忠实模仿错误的模式；示例太多会占满上下文。
要求分步思考 每生成一个 token 都要走一次完整前向，所以"写出中间步骤"等于把一次浅层预测拆成多次串行计算，有效增加了计算深度。 简单任务上属浪费；推理模型的思维链已内化，再要求外显反而干扰。
用分隔符 / 标签包住材料 给注意力提供清晰的边界锚点，让模型能区分"指令"与"数据"，减少两者混淆；同时也降低了材料里的文字被当成指令执行的风险。 分隔符本身没有语义，靠的是训练中形成的惯例；冷门符号效果不稳定。
指定输出格式 缩小搜索空间：格式约束排除掉大量候选序列，等效于提高目标序列的概率。JSON / 表格比自然语言段落更"尖"。 格式与模型习惯差异过大时（如要求罕见标记），模型可能牺牲内容去满足格式。
"不要做 X" 依赖指令微调训练出的否定理解能力。指令微调把"指令—服从"这一格式本身变成了强先验，所以格式化的祈使句有额外权重。 长上下文中否定约束衰减快；多个否定叠加时模型容易"只记住被禁止的词"。正向描述通常更稳。
关键指令重复一遍 对抗中间遗忘：位于长上下文中间的内容被利用率显著低于首尾。开头立规矩、结尾再重申，是低成本的补偿。 重复太多次会诱发"复读"倾向，也可能让模型把重复本身当成本任务。

4.4 结构性失效：不是"模型笨"，是架构使然

  • 首尾效应。序列开头与结尾的信息被利用率最高，中段最容易被"看过去"。这不是注意力不够，而是相对位置在训练分布中的统计结果。
  • 注意力预算稀释。上下文越长，每个 token 分到的份额越少。塞入大量无关材料，会实打实地降低关键指令的权重——"给得越多越好"是错的。
  • 补全而非检索。模型没有数据库查询机制，事实来自参数记忆与上下文，二者冲突时它会倾向于生成"最顺滑的续写"，而顺滑与真实并不总是同向。这就是幻觉的机械来源。
  • 指令层级不稳。系统层、开发者层、用户层、材料层的内容在模型眼里最终都只是 token 序列，优先级靠训练与位置维持，而非硬性隔离。任何把不可信内容混进指令区的做法都会削弱这层秩序。
  • 格式漂移。输出越长，早期建立的格式约束衰减越明显。长文档生成到后段忽然改格式，是采样逐步偏离的必然结果，不是"忘了"。
  • 硬预算。上下文窗口是物理上限，超出即截断。任何"把全部资料都塞进去"的策略最终都会撞上这堵墙。

4.5 约束解码：把"请求"升级为"保证"

第四部分的最后一块拼图，正好接上第二部分家族 C。前面说过提示词只能影响概率，但在工程里我们常常需要保证格式。这中间有三档强度，成本与确定性同步上升：

层级实现方式确定性典型代表
软约束 在提示词里写清楚 schema，附示例，请求模型照做 高概率，偶尔破格 任意模型 + 模板
半硬约束 服务端提供的 JSON mode / function calling / 结构化输出参数 很高，仍可能语义错 各家 API 的结构化输出
硬约束 客户端把语法编译成状态机，逐步对 logits 掩码；或前缀强制 结构 100% 合法 guidance、outlines、llama.cpp 文法

硬约束的代价要说清楚：掩码会剥夺模型"本来想说的更好的表达"。当语法不允许某种自然措辞时，模型只能在狭小的合法集合里挑一个，可能挑出语法完美但语义空洞的结果。约束解决的是"能不能被程序解析"，不解决"内容对不对"。这也是为什么家族 C 必须与家族 B 配合使用——一个保证形状，一个保证质量。

全篇收束成一句：提示词生成器的一切技术，最终都落在两个杠杆上——要么往条件里补信息（模板、示例、上下文、检索），要么往输出上收约束（格式、schema、文法、类型）。前者提高"答对的概率"，后者降低"答错的空间"。所有开源方案与产品设计，都是这两个杠杆的不同配比。
